## Findings and disposition

The findings below describe the reviewed revision. **All four now have fixes and
regular regression tests**, described in the remediation section below. External
broker guarantees and instrument profiles remain unresolved. No trading policy
was changed by this review or its remediation.

### R1 — High: incomplete discovery can permanently block subsequent runs

Accepted Fable concern 1. `Workflow.acceptScan` mutates and saves `SourceBook`
before rejecting an incomplete scan. An update whose opening failed parsing can
be saved as an orphan. After the parser is fixed, `SourceBook.apply` skips that
identical update because its hash is already recorded. The old global blocker
also remains. A corrected scan cannot heal the book, including after restart.
`Main` aborts before evaluation, so exits and stop changes are blocked too.

Recommendation: retain raw observations separately from accepted source state;
stage source reconstruction and validate it before advancing accepted state.
Provide a tested recovery/rebuild path that preserves broker participation,
completed events and attempt history. Do not blindly rebuild trading state or
automatically approve materially revised instructions: those still require review.

Probe: `incompleteScanPoisonsBookEvenAfterCorrectedRescanAndRestart`.
Fable's additional same-day lexical post-ID ordering concern is plausible from
the comparator but was not separately reproduced here.

### R2 — High: a filled order with missing protection blocks its own repair

Accepted Fable concern 2, with the broker-dependent trigger kept explicit.
`EtoroClient.observe` returns PARTIAL with `COPY_OR_STOP_NOT_CONFIRMED` when
filled agent/copy positions lack the exact fixed stop. The executor records the
known position IDs, but `Workflow.evaluate` returns for unresolved attempts
before reaching protection or reductions. Repeated runs leave that condition
unchanged. No live incident is claimed: the workflow stall was reproduced using
a synthetic filled, unprotected position; adapter stop checks were inspected.

Recommendation: distinguish unknown execution from known exposure awaiting
protection. Report the exact unprotected account/position urgently and permit
only reconciled, narrowly scoped protection recovery. Do not unblock purchases.
An owner-copy-only stop failure may not be repairable through the agent API;
that requires a supported recovery procedure, not an assumed API capability.

Probe: `knownFilledUnprotectedLotNeverReachesProtectionPass`.

### R3 — High: a conflicting close is silently omitted

Accepted Fable concern 3. A close with a mismatched before-weight sets only the
cycle's `WEIGHT_CHAIN_MISMATCH` blocker, then marks the source cycle closed.
The closed cycle is excluded from dashboard comparison, allowing scan acceptance.
Reduction and protection return empty lists because the cycle is blocked.
With the existing stop matching, evaluation produces an empty report while the
actual holding remains open.

Recommendation: every held instruction must produce an explicit report showing
the symbol, conflicting source facts, retained exposure and required resolution.
Keep the agreed hold-on-ambiguity policy; do not silently execute the bad input.
Surface blocked work in command outcome as well as the durable report.

Probe: `mismatchedCloseIsAcceptedThenSilentlySkipped`.

### R4 — Medium: a kill-cancelled close cannot resume after the kill is removed

Additional primary-agent finding. If the kill switch appears during preparation,
the executor journals `KILL_BEFORE_SUBMISSION` as REJECTED without sending the
close. After the owner removes the switch and restarts, the durable reduction
batch reuses the same intent key. `Executor.execute` returns that old rejected
attempt, and reconciliation deliberately skips it. The close never submits;
the workflow also returns before later work. Opening/addition attempts have
numbered retries, but risk-reducing batches do not.

Recommendation: retain the original batch and confirmed members, and support a
fresh attempt for a member proved never submitted, with new reference and fresh
holding checks. Do not retry unknown outcomes or repeat confirmed reductions.

Probe: `closeCancelledByKillBeforeSubmissionCannotRetryEvenAfterRestart`.

## Implemented remediation

- R1: reject incomplete scans before applying observations; validate complete
  scans on a copy before accepting them. Preserve rejected observations and
  reasons privately under `state/runtime/source-review/`. Replay old unattached,
  unrevised orphans on a corrected complete scan. Preserve participation, attempts,
  completed events and holding baselines. Numeric WordPress IDs sort numerically.
- R2: report unprotected agent and copied positions explicitly, including on the
  first unresolved submission. On subsequent owner runs, allow only agent-stop
  repair for a known PARTIAL fill with matching source stop and verified fresh
  account/position evidence. Unknown execution, pending broker activity, changed
  stops, ambiguous source and identity discrepancies cannot authorize a repair.
  Confirm protection through broker reads; do not purchase during recovery.
  Copy-only failure remains an explicit owner intervention case because there is
  no supported owner-side write capability in this program.
- R3: report blocked close instructions with their source weights and retained
  agent units. The command signals blocked/unresolved work with exit code 2.
- R4: retry only attempts proved cancelled by the kill switch before submission,
  using a new UUID and preflight. Retain the original batch, reuse confirmed
  members and never retry an unknown execution.

The old characterization task was removed; desired-behaviour tests now run in
the regular JUnit suite, coverage and PIT targets. Use `. ./env.ps1` then
`gr check pitest`. [Engineering](../ENGINEERING.md) records verification totals.
The original Fable review above is unchanged; no additional consultation was made.
