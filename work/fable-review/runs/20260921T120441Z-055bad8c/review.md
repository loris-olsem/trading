## Overall assessment

The core discipline is genuinely strong: write-ahead attempts with durable batches, cross-checked dual-endpoint account reads, read-only owner-key verification, fail-closed defaults everywhere, and dry-run paths that verifiably never reach `submit` (`Workflow.batch` returns before submission when not live, and `EtoroClient` refuses writes when constructed read-only). I found no path to duplicate submission or invented stops. My three material concerns are all about the other failure family: fail-closed states that cannot heal, and one silent skip of a risk-reducing action.

## Concern 1 — a routine scan anomaly can permanently wedge the whole system, with no heal path (confirmed from code)

`Workflow.acceptScan` applies alerts into the durable book *before* checking `scan.complete()` (Workflow.java:71–77). `SourceBook.apply` records each alert in `revisions` and skips any later identical observation (SourceBook.java:20–22), and `book.blockers` is never cleared. Post-initialization there is no `initialBook` rebuild. Trigger: a new cycle's OPEN article fails to parse (rehearsal already hit grammar variance) while its follow-up update parses → `ORPHAN_UPDATE` is persisted; after you fix the parser and rescan, the identical update is skipped by the revisions dedupe and the blocker remains, so `acceptScan` throws forever (Workflow.java:76–78) and `evaluate` — including every CLOSE/REDUCE on every symbol — never runs (Main.java:170–178). `REVISED_INSTRUCTION` (Bravos editing an old article) wedges identically. A latent extra trigger: same-day alerts sort lexicographically by `bravos:post:NNN` key, which misorders across post-id digit lengths. operations.md says "extend parser and rediscover," but rediscovery cannot heal this; only manual ledger surgery can, which the same doc rightly discourages. Suggest: refuse to mutate the book from an incomplete scan, and recompute blockers/held alerts from `revisions` on each apply so a corrected scan can heal.

## Concern 2 — a filled-but-unprotected position deadlocks protection (confirmed structure; broker-dependent trigger)

`evaluate` returns early while any attempt is not CONFIRMED/REJECTED (Workflow.java:97–102). But `observe` only confirms an OPEN/ADD once agent and copies carry the exact stop (EtoroClient.java:283–287), and the only mechanism that installs a missing stop — the protection pass at Workflow.java:196–199 — sits behind that early return. If eToro fills the limitIOC open but drops the `stopLossRate` (or the copy doesn't inherit it — exactly the open broker-contract question), the attempt stays PARTIAL forever, the live position sits unprotected indefinitely, and all future reductions are frozen behind a generic `UNRESOLVED_ORDER_BLOCKS_NEW_SUBMISSIONS`. Suggest: permit STOP-repair intents for an unresolved attempt's known `positionIds`, or at least report `UNPROTECTED_POSITION` explicitly so the owner knows to intervene.

## Concern 3 — `WEIGHT_CHAIN_MISMATCH` silently suppresses closes (confirmed)

`SourceBook.apply` sets only `c.blocker` for a before-weight mismatch, not `book.blockers` (SourceBook.java:57–58), and still applies the event. If the mismatched alert is the CLOSE (a plausible human typo in "from X% to Y%"), the cycle goes `sourceOpen=false`, so `dashboardMatches` ignores it, `acceptScan` passes, and `Policy.reduction`/`protection` return empty for the blocked cycle (Policy.java:143, 180) — the position is held indefinitely against the source's exit with *no report line at all*, since nothing in the reduction path surfaces `c.blocker`. Holding is the agreed policy; holding silently is not.

## Recommendation

Proceed with the architecture as built — it is sound and the broker blockers remain the true release gate — but fix the book-heal path (concern 1) and the protection deadlock (concern 2), and make cycle blockers loud (concern 3), before initialization/live enrollment. All three are cheap relative to the recovery cost of hitting them live, and tests should cover exactly these wedge scenarios since the current suite evidently shares production's assumption that blocked states eventually resolve.
