## Verdict: revise — one justified code change, one evidence-based experiment, and an honest constraint conflict to surface

**Acceptance criteria.** The user's goal is a working trading app, which here means: at least one verified agent fill at or below the strict ceiling, with the exact Bravos stop, and the owner copy verified by read-back — not accepted orders, not green tests. Secondary criteria: no doomed submissions the app could have predicted, and no silent loosening of price/stop policy.

**What I inspected.** `docs/ETORO-1065-INVESTIGATION.md`, `docs/broker-contract.md`, `config/trading.json`, `OrderPayloads.java`, `EtoroClient.java` eligibility/preflight (lines 180–309), and the captured spec `state/etoro-openapi.json`: the real v3 path (line 33333) and `TradingRealAdminApi_UnifiedOrderRequest` (line 46025). The ledger confirms the 1065 rejections are journaled verbatim. I did not verify live broker behavior — nobody can from this checkout.

**Concern 1 (defect, fix justified now): CFD + limitIOC is structurally impossible, and the app still builds it.** Broker error 2039 states it outright, and the spec supports it: `limitRate` is "the client submitted price which will be routed to the exchange" (line 46159) — a CFD has no exchange to route to. Yet `OrderPayloads.create` explicitly accepts `"cfd"` settlement for limitIOC opens (`OrderPayloads.java:22`), and `EtoroClient.openingConfiguration` validates the configured settlement without checking order-type compatibility. Consequence: ARGT submissions are deterministically doomed, and SMH will fail identically once under its ceiling. The justified change is a preflight/payload gate rejecting limitIOC on non-real settlement, classifying those assets as unexecutable under current policy. Note this means ARGT/SMH cannot be traded *at all* with a strict ceiling — mkt/mit don't cap price — which is an owner decision to surface, not an app fix.

**Concern 2 (diagnosis of 1065): deterministic, not connectivity; the units experiment has a real, narrow basis.** Seven rejections across two API versions and three instruments is not a transient "connectivity issue"; the message describes an unavailable routing path ("HBC only path") behind an OrderValidation code. The spec documents no 1065 and eligibility has no limitIOC flag, so no further endpoint/field swap is evidence-based. But one documented distinction remains: limitIOC is exchange-routed, exchanges match whole shares, and all seven orders were amount-sized producing fractional quantities (~1.58 BRK.B, ~1.28 ADI, ~3.27 EOG). The eligibility schema itself distinguishes `whole` vs `fractional` quantity and `fillOrKill` vs `bestEffort` fill behavior (lines 41592–41602), showing quantity semantics vary by path. A whole-units limitIOC attempt is therefore the one owner-operable experiment that discriminates "fractional/amount sizing unsupported on the exchange path" from "agent account lacks the route." It preserves the ceiling and exact stop; the sizing shortfall from flooring to whole units fits the already-approved "keep the partial fill; report the shortfall" decision; copy verification must then check proportionality against the actual invested amount from read-back rather than the requested amount. This is a hypothesis to test, not a fix to announce — prior probability is genuinely uncertain.

**Concern 3 (the honest limit): if whole-units also returns 1065, no app change can satisfy the constraints.** The user's constraints — strict ceiling, no support contact, must actually trade — become mutually unsatisfiable, because the only capped order type on this API would be unavailable to this account, and that is a broker enablement matter. The app's correct behavior then is precise evidence and a clear report of the conflict, which the packet's framing ("do not call an unfilled order a working application") already accepts. Minor addition: the documented 10% limit-vs-market pre-trade deviation rule (line 46159) is currently unpreflighted; add the check so a future market move doesn't produce a second, confounded rejection mode.

**Strongest challenge:** that the whole limitIOC-strict-cap architecture is unsupportable for agent accounts and any further work is wasted. The evidence cannot defeat this — which is exactly why the verdict is qualified rather than an endorsement: implement the CFD gate, run the whole-units experiment once, and if it fails, report the constraint conflict to the owner instead of iterating further endpoint changes. The primary agent's refusal to treat green tests or better errors as success is correct and should be preserved.
